## 3. 功能概述（Functional Overview）

定义一个虚构商贸场景，集中处理订单从提交到履约、结算和售后调整的完整过程。客服可了解订单处理结果，仓库人员可处理库存分配和发货，结算人员可处理失败与差异，日终操作员可查看批次结果。系统需要在修改、取消、部分履约、重复请求和失败恢复过程中保留一致且可追踪的业务记录。

## 4. 业务背景（Business Context / Background）

- **业务领域**：完全虚构的多仓商品订单处理。
- **虚构问题**：订单、库存、履约和结算状态容易因部分处理、重复消息或失败重试而不一致，操作人员需要知道每笔业务停在哪里及下一步由谁处理。
- **虚构使用方**：客服、仓库、结算及日终运营人员。
- **本项目动机**：构造可阅读的大型遗留风格源码，观察模型是否能还原处理路径、数据变化、系统交接和业务交易生命周期。
- **资料来源边界**：仅使用本文构造的业务；不采集真实业务、生产数据、人员、系统或网络信息。

## 5. 业务目标（Business Objective）

使每笔订单的受理、分配、履约、结算及售后结果可追踪，使重复处理不会重复消耗库存或重复结算。业务失败应留下明确的处理结果和恢复入口；日终结果应能够区分已确认结算、待处理及异常事项。

## 8. 目标业务过程（Future Process / Desired Behavior）

1. **提交及受理**：客服或订单接入端提交订单；得到受理或拒绝结果，重复请求应返回已知结果。
2. **校验及计价**：根据虚构客户、商品和价格资料检查订单并计算金额；不合格订单说明原因。
3. **库存分配**：按虚构仓库优先次序分配。允许部分履约的订单可先分配可用数量；其余等待后续补分配。
4. **修改或取消**：首次发货前可提交修改；任何阶段均只能取消尚未发货的剩余数量。已发货部分走退货流程。
5. **履约及结算**：仓库确认实际发货数量，结算端确认相应金额；结算失败不应抹去已发生的发货事实。
6. **售后调整**：在规定窗口内对已结算发货办理退货，归还库存并形成原结算的反向调整。
7. **恢复及反馈**：操作人员区分业务失败、结果未知和回执失败，分别处理；不能将发送回执失败当作业务整体失败。
8. **日终处理**：汇总本处理日已确认的正向及反向结算，另列待处理和异常清单，支持追溯到原请求和订单。

业务轨迹需要同时呈现订单办理、库存／履约、结算和回执进度。它们可能不同步，例如“已发货、结算失败、回执已送达”；不得用一个笼统的“失败”覆盖所有进度。

## 10. 业务规则（Business Rules）

以下规则均为本项目合成设定。BR 编号在后续文档和源码追踪中保持不变；金额只是测试计量单位，不对应真实货币结算。

### 受理与校验

| 编号 | 规则 |
| --- | --- |
| BR-01 | 所有业务请求必须具有来源、请求标识、业务类型和处理日；缺少任何一项均拒绝受理。 |
| BR-02 | 新订单和订单修改只允许使用存在且启用的客户。 |
| BR-03 | 新订单和订单修改的所有明细必须引用存在、启用且有正数有效单价的商品。 |
| BR-04 | 每条订单明细数量必须为 1～9,999 的整数。 |
| BR-05 | 一张订单必须包含 1～100 条明细；明细序号在订单内唯一。 |
| BR-06 | 同一来源和请求标识、相同业务内容的重复请求必须返回最近已知结果，不重复占用、发货或结算；“重新尝试失败业务”需要独立的恢复动作。 |
| BR-07 | 同一来源和请求标识携带不同业务内容时，拒绝为冲突请求，保留第一次请求及其结果。 |
| BR-08 | 已存在的订单不能用新请求标识再次作为新订单创建；后续动作必须引用原订单。 |
| BR-09 | 修改、取消、分配和发货请求须基于当前订单版本；版本过期时拒绝该动作，不改变当前业务记录。 |

### 修改、计价与分配

| 编号 | 规则 |
| --- | --- |
| BR-10 | 订单只有在尚无发货记录、且没有全部取消时才可修改；修改需要重新校验、计价及安排分配，修改未被接受时保持原订单与原占用。 |
| BR-11 | 客户分普通和优选两级：普通按有效单价计价，优选享 5% 折扣；不叠加其他折扣、税费或运费。修改使用修改受理时的有效价格和客户等级。 |
| BR-12 | 每行金额按数量、单价及客户折扣计算，四舍五入保留两位小数；整单金额等于已舍入的各行金额之和。首次发货后保留原计价依据，不能因价格资料变化重算已受理订单。 |
| BR-13 | 仅从启用仓库分配，固定优先次序为演示仓库 A、B、C；同一订单按明细序号分配。 |
| BR-14 | 可分配数量为现有库存扣除已占用数量，分配不得使可用数量为负；发货同时减少现有库存及对应占用。 |
| BR-15 | 不允许部分履约的订单，仅在整单剩余数量均可满足时分配，否则整单剩余数量等待且不新增占用；允许部分履约时可先分配可用数量，其余等待。 |
| BR-16 | 后续补分配只处理尚未分配、发货或取消的有效需求；新到库存不会触发重复占用已有分配。 |

### 履约、取消与退货

| 编号 | 规则 |
| --- | --- |
| BR-17 | 每次发货数量必须为正整数且不超过该订单明细在指定仓库的尚未发货占用；一次确认涉及多条明细时，全部满足条件才接受该次确认。 |
| BR-18 | 取消数量必须为正整数且不得超过未发货、未取消数量；先取消未分配部分，不足部分按 C、B、A 的次序释放占用。 |
| BR-19 | 已发货数量不得通过取消回退；全部剩余数量取消后不再接受该订单的新分配和修改，已有发货仍允许完成结算及符合条件的退货。 |
| BR-20 | 退货只能引用已成功结算的原发货明细；每次退货数量须为正整数，累计退货数量不得超过该明细已发货数量，退货处理日与发货业务日相差须为 0～30 个自然日（含边界）。 |
| BR-21 | 接受退货后将数量归还到原发货仓库，但不重新增加原订单待分配需求；即使该仓库已停用，归还数量也只记为该仓库库存，不供新订单分配。 |
| BR-22 | 退货调整沿用原发货结算金额。按累计退货数量比例计算累计应调整额，再扣除此前已成功调整额；全部退回时累计调整必须等于原发货结算金额。同一原发货明细仍有未完成调整时，后续退货暂不受理且不增加归还数量；原调整沿既有身份恢复，不重复创建。 |

### 结算、恢复与日终

| 编号 | 规则 |
| --- | --- |
| BR-23 | 结算只针对已确认发货，且每次发货只形成一项正向结算。分次发货按原订单行金额的累计发货比例分摊到两位小数，本次金额为累计应结算额减此前已分配给发货的金额，全部发完时正好等于原行金额。 |
| BR-24 | 明确的结算失败保留已发货或已接受退货事实，标为待恢复；结算结果未知时保留为待核实，核实前不能再次发起结算或宣告成功。 |
| BR-25 | 已确认可重试的失败沿用原结算或调整身份重试，不创建第二笔业务；成功结果不得被后到的失败通知覆盖，重复成功通知不重复计入金额。 |
| BR-26 | 回执发送失败只允许重送回执，不重做已完成业务；回执应同时反映业务结果和最近送达情况。 |
| BR-27 | 批次中的业务拒绝只影响该请求，其余独立请求继续；每条请求的受理结果及等待／失败原因可单独查询。 |
| BR-28 | 恢复中断批次时跳过已完成请求，从未完成请求继续；“结果未知”的外部结算先核实，不能因重跑批次而重发业务。 |
| BR-29 | 业务处理日由输入明确指定；演示运营日以 18:00 为接单截点，18:00 及之后到达的请求归下一处理日。涉及重复识别时，重送保留原请求处理日，不重分日期。 |
| BR-30 | 日终金额按本处理日已确认成功的正向结算减本处理日已确认成功的退货调整汇总；待处理、失败和未知结果另列，历史成功记录不因后来退货而从历史汇总消失。 |
| BR-31 | 人工处置须保留操作者、原因及所选择的恢复动作；不能直接覆盖成功结算、抹去原失败或跳过数量和状态校验。 |
| BR-32 | 请求、订单、明细、发货、退货、结算、调整、回执和处理批次均能沿关联标识追溯；拒绝、等待和重试也须保留可解释的业务结果。 |

### 规格阶段的合成边界解释

- BR-10 的修改采用发货前完整替换版本。旧版本的订单行、取消及占用历史保留在审计，新版本重新计价、分配；库存不足可以是已接受但等待的结果，校验或本地写入失败则保持原状。
- BR-17 的一张发货确认允许同一订单行从多个仓发货，但同一行／仓组合不得重复；分摊按订单行及仓库稳定排序。仓库停用只限制新分配，不阻止履行已有占用。
- BR-20～BR-22 的一次退货限定同一订单，可以引用多个原发货，但不得重复引用同一原发货明细。因原调整未完成而暂不受理时不归还库存；通过显式恢复重新校验后才能接受。
- BR-23 在部分发货后取消余量时仍沿原冻结数量和金额按实发比例结算，不因取消余量补收整行金额。
- FR-13 / BR-30 的待处理金额清单包含尚未完成的结算／调整，并另列本地待恢复请求。库存履约缺口通过订单查询展示，不计入待结算金额。

这些约定用于补齐已授权的虚构场景，不来自真实业务。字段、编码、参数和精确步骤见[规格索引](../specifications/README.md)。

| 演示接入／仓储／结算对端 | 提供与接收业务信息 | 输入业务请求或确认结果，接收相应输出。 |

日间业务按事件发生；日终由演示操作员在截点后发起。BR-29 的截点是本项目提供的操作背景，不能假称为从 RPGLE 推导出的事实。职责只定义业务边界，不要求实现真实登录和权限平台。

| E-05 | 发货或取消数量超出允许范围 | 拒绝该次动作，不产生部分成功。 | High |
| E-06 | 退货超期、超量或原发货尚未成功结算 | 拒绝退货，不增加库存或形成调整。 | High |
| E-07 | 正向结算或退货调整明确失败 | 保留已发货／已退货事实，交结算人员恢复。 | High |
| E-08 | 无法确认对端是否已经结算 | 保持待核实，不自动重复提交。 | High |

| E-11 | 已成功后收到重复或相矛盾的通知 | 不覆盖成功、不重复计账，保留通知及差异。 | High |

| 编号 | 场景与预期结果 | 覆盖 |

## 16. 假设与约束（Assumptions / Constraints）

### 明确的合成设定

- 单一虚构经营主体，三个有序演示仓库，普通／优选两类客户，单一测试金额单位。
- 处理日使用连续自然日；不模拟节假日或时区换算。18:00 截点属于演示业务背景。
- 退货作为原发货的售后交易，已完成订单仍可在窗口内办理退货；不重新开启原订单履约。
- 新订单不合格时整体拒绝；库存不足通过等待／部分分配表达，不混同于资料校验失败。
- 价格、阈值、数量及舍入要求均为虚构规则，不声称符合任何真实行业制度。

- [README 的 BC-01～BC-09](../../README.md#本项目的评测与样本约束)适用于后续所有阶段。
