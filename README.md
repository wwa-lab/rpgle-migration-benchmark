# RPGLE 内外网模型对比评测

使用完全虚构的「多仓订单履约与结算」样本，比较模型对大型固定格式 RPGLE 的静态理解能力。重点为 Operation Flow、System Flow、Data Flow 和 Transaction Flow；Program Flow 是交易路径分析的基础证据。

本项目不需要真实业务、公司源码、内部系统名称或真实交易数据。合成样本的结果用于说明对所设计场景的分析表现，不代表已经验证真实核心系统的迁移效果。

## 本项目的评测与样本约束

本节是样本规模、格式、评测输入和执行边界的唯一维护位置；业务内容以功能需求文档为准。

| 编号 | 约束 |
| --- | --- |
| BC-01 | 全部业务、角色、系统、字段、规则和示例由本项目虚构；不要求用户提供真实业务资料。 |
| BC-02 | 生成一个主程序，目标为单文件 10,000～12,000 个物理行；分别报告总行数、空行、注释行和非空非注释行。通过业务分支形成体量，不以复制语句、注释或声明堆积凑行数。 |
| BC-03 | 主程序及配套 RPGLE 均使用固定格式，保持列位置；即使属于新程序，也覆盖上游的 New Program → Free Format 默认值。CLLE、DDS 按各自格式处理。 |
| BC-04 | 配套目标为 4～6 个 RPGLE 程序、CL 驱动以及必要的 DDS、COPY 和接口背景。当前设计及源码采用 6 个配套 RPGLE、1 个 CL 驱动、24 个 DDS 和 3 个 COPY；职责以技术设计和规格为准。 |
| BC-05 | 本阶段只做文档和源码静态检查，不编译、不运行 IBM i 程序，不连接真实业务系统，不生成或执行测试数据装载脚本。静态预检不得标记为已通过编译或运行验证。 |
| BC-06 | 四类 Flow 的含义按下表固定。Operation Flow 不等同于程序内部执行步骤，System Flow 不等同于程序调用图。 |
| BC-07 | 评测包与评审参考材料分离；两边收到相同版本的输入，不向被测模型提供需求全文、生成过程、完整答案或规则到源码的评分映射。 |
| BC-08 | 两边固定提示词、文件集合、分批策略、工具权限和追问规则，并记录实际模型配置及输入限制。模型选择和部署配置在运行前核实，不属于本轮交付。 |
| BC-09 | 所有生成需求及评审参考均属于合成场景定义；源码行为应以静态阅读的证据核对，不把设计意图自动当成实现事实。 |

## 四类 Flow 的目标

| Flow | 要回答的问题 | 需要提供的输入 |
| --- | --- | --- |
| Operation Flow | 谁发起业务、在什么时点处理、人工介入在哪里、正常及异常结果如何交接？ | 简短的虚构角色、操作流程、处理日和异常处置说明；源码补充具体行为。 |
| System Flow | 虚构订单接入端、核心处理端、仓储端、结算端及报表端如何协作，边界和接口是什么？ | 简短的虚构系统与接口说明，以及源码中可见的接口入口和出口。 |
| Data Flow | 关键数据从哪里来，如何计算和变化，传给谁，写到哪里，异常对数据产生什么影响？ | RPGLE、CLLE、DDS、COPY、必要的接口字段说明。 |
| Transaction Flow | 一次提交、分配、履约、取消、退货或重试如何跨程序推进，并到达成功、拒绝、等待或失败结果？ | 同一套源码及依赖；用 Program Flow 支撑调用关系、条件、状态和结果追踪。 |

后续统一分析交付为四类流程图、解释、来源位置及未知事项。Program Flow 可作为 Transaction Flow 的支撑图或证据表，不额外要求第五份业务视图。这里的 Transaction 是业务交易生命周期；源码中若有数据库事务边界，应另外解释，不能由业务名称推断提交或回滚行为。

## 材料边界

当前材料分为以下目录：

- `benchmark/input/`：冻结后的源码、依赖、必要的操作背景和接口说明。背景只补充代码之外的上下文，不附完整规则答案或逐条解析。
- `benchmark/reference/`：四类 Flow 评分参考、源码证据、变换与静态核验记录；完整需求和设计仍在 `docs/`，仅供生成与评审使用。
- `benchmark/runs/`：两边模型配置及运行／评分模板，后续保存原始结果及人工比较记录。
- `benchmark/prompts/`：统一提示词母版；各交付包附对应使用版本。
- `benchmark/dist/`：可分别交付的文件版与分段文本版压缩包。

开发源码可以保留上游技能要求的 BR/Step 追踪信息。打包评测版时检查注释是否泄露完整规则或评分映射，并记录开发版与评测版的变换及各自版本、行号；不能直接把整个项目交给被测模型读取。

## 后续流水线

本项目使用复制的 IBM i 技能作为主工作流，不另建 Spec Kit、OpenSpec 或另一份独立需求主文档。

1. **需求文档（草案已完成）**：`ibm-i-functional-spec`。直接生成 Functional Spec；不额外重复一份需求归一化文档。
2. **技术设计（草案已完成）**：`ibm-i-technical-design`，从功能需求分配职责、确定边界和完整依赖。
3. **程序与文件规格（草案已完成）**：`ibm-i-program-spec` 和 `ibm-i-file-spec`，继承 FR/BR 编号，先统一数据及共享定义，再补齐各程序参数和处理细节。
4. **源码与 DDS（草案已完成）**：`ibm-i-code-generator` 和 `ibm-i-dds-generator`；固定格式约束同时传入生成和审查。
5. **静态审查（本轮结构检查已完成）**：已按 `ibm-i-code-reviewer` 做针对性审阅；检查项与局限见 [检查记录](docs/source/validation-report.md)。这不代表编译、运行或全部业务行为已获验证。
6. **评测打包（已完成）与比较（未运行）**：已隔离输入／参考材料并冻结 RPGFLOW-1.0。两端先核实实际配置并选定同一种交付方式，再进行模型分析。

`ibm-i-ut-plan-generator`、`ibm-i-test-scaffold` 已随上游复制，但在当前范围中不启用。`ibm-i-workflow-orchestrator` 后续可用于路由；当前不创建或执行它的批量 `task.md`。
